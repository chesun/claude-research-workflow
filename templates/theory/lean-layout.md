# Lean project layout for a theory project (ADR-0004, phase 2)

One Lean project per theory project, **outside OneDrive** (Lean is slow on synced folders), e.g. `C:\Users\<you>\lean\<project>`. The theory repo points at it, and at the checking tools, in its gitignored `.claude/state/lean.toml`:

```toml
project = "C:/Users/<you>/lean/<project>"
comparator = "C:/Users/<you>/lean/_tools/comparator/.lake/build/bin/comparator.exe"
lean4export = "C:/Users/<you>/lean/_tools/comparator/.lake/packages/lean4export/.lake/build/bin/lean4export.exe"
landrun = "C:/Users/<you>/lean/_tools/comparator/scripts/fake-landrun.cmd"   # Linux: the real landrun
```

Back the Lean project up: give it a private remote once real proofs exist. A `verified` node can only be re-checked while its Lean files exist.

## Setup (once per machine)

- **Lean:** elan from its GitHub release (verify the asset's SHA-256), with `--default-toolchain none`.
- **Comparator** (Lean FRO's proof judge, the reference manual's "gold standard"):
  - clone `https://github.com/leanprover/comparator` into `~/lean/_tools/comparator`, at a commit whose `lean-toolchain` matches the project's;
  - run `lake build lean4export comparator` there.
- **Windows:** comparator's sandbox, `landrun`, is Linux-only. Use its development shim `scripts/fake-landrun.sh` through a one-line `scripts/fake-landrun.cmd`:

  ```
  @echo off
  "C:\Program Files\Git\usr\bin\bash.exe" "<path>\comparator\scripts\fake-landrun.sh" %*
  ```

  There is no sandbox on Windows. `lean_check`'s project scan (below) is the defence in depth. `lean_check` puts Git's `usr/bin` on the tools' PATH, because comparator calls `which` and `git`, which PowerShell sessions often lack.

## Setup (once per project)

```
lake +leanprover-community/mathlib4:lean-toolchain new <project> math
```

Then make `lakefile.toml` **canonical**. comparator trusts the lakefile, so `lean_check` accepts only this shape (the option values may differ):

```toml
name = "<project>"
version = "0.1.0"
defaultTargets = ["<Pkg>"]

[leanOptions]
autoImplicit = false
relaxedAutoImplicit = false
weak.linter.mathlibStandardSet = true   # optional; style lints are warnings, not failures

[[require]]
name = "mathlib"
scope = "leanprover-community"
rev = "v4.35.0-rc4"

[[lean_lib]]
name = "<Pkg>"
globs = ["<Pkg>.+"]

[[lean_lib]]
name = "LeanCheck"
globs = ["LeanCheck.+"]
```

- **The lakefile:** no `lakefile.lean`, no `srcDir`, `roots` or extra arguments, no other `require` or target.
- **The dependency manifest:** `lake-manifest.json`, which Lake writes, must:
  - fetch every package from a `leanprover` / `leanprover-community` GitHub repo, pinned to a 40-hex commit;
  - have Mathlib's `inputRev` equal the lakefile's `rev`;
  - keep the default `packagesDir`.

  `lean_check` also confirms each checked-out package under `.lake/packages` is at its pinned commit.
- **leanOptions** may only be `pp.*`, the two `autoImplicit` flags, `linter.*` / `weak.linter.*`, `maxSynthPendingDepth`, `maxHeartbeats` and `maxRecDepth`.
- **`.gitignore`:** add `/LeanCheck`.
- **git:** run `git config core.autocrlf input`.

**Toolchain and Mathlib bumps** are deliberate acts. Move comparator to a matching commit, then re-run `lean_check` on every `verified` node. A new failing report takes the node's verification away.

## Files (package `<Pkg>`, node file stem `<Name>`)

| File | Holds | Rule |
|---|---|---|
| `<Pkg>/Statements/<Name>.lean` | everything the owner audits: helper `def`s and the `<x>_stmt : Prop` defs | self-contained; imports only Mathlib; **the whole file is hashed onto the card** |
| `<Pkg>/Proofs/<Name>.lean` | `theorem <x> : <x>_stmt` for every `<x>_stmt` | imports its statement file |
| `LeanCheck/<Name>{Challenge,Solution}.lean`, `LeanCheck/<Name>.comparator.json` | generated by `lean_check` for comparator | never hand-edited; gitignored |

The node's header gets `lean: <Pkg>.<Name>`.

### Statement file

```lean
module

public import Mathlib

set_option linter.style.header false

@[expose] public section

/-! <Node label>: one line on what this file states. -/

namespace <Pkg>

/-- Plain-English docstring for every helper. -/
noncomputable def postVar (s0 x n : ℝ) : ℝ := s0 * x / (n * s0 + x)

/-- (a) ... -/
def nstarAC_part_a_stmt : Prop := ∀ s0 x c : ℝ, 0 < s0 → 0 < x → 0 < c → ...

def nstarAC_nonvacuous_stmt : Prop := ∃ s0 x c : ℝ, 0 < s0 ∧ 0 < x ∧ 0 < c ∧ ...
def nstarAC_sanity_1_stmt : Prop := ...        -- a concrete instance matching a numeric check file
def nstarAC_false_variant_stmt : Prop := ¬ ... -- a plausible wrong version, refuted

end <Pkg>
```

- **`@[expose] public section` is required.** Under the module system a definition's body is hidden from other files unless exposed, and the proofs must `unfold` the statements.
- **Allowed commands:** `module`, `public import Mathlib…`, `set_option linter.<name> false`, `@[expose]`, `section`/`namespace`/`end`, `def`/`noncomputable def`/`abbrev`/`structure`/`inductive`, and `open X` (but not `open X in`).
- **Names:** every definition has a plain ASCII name without dots, so it cannot pass for or shadow another name. Invisible characters such as zero-width spaces are rejected. `open … in`, `renaming` and `hiding` are not allowed.
- **Not allowed, at any indentation:** `variable`, `universe`, notation, macros, `instance`, `theorem`, `axiom`, `attribute`, `deriving`, `mutual`, any `@[…]` other than `@[expose]`, a second namespace, declarations after `end <Pkg>`, or any import other than Mathlib. A reader must be able to see every assumption in the file itself.
- **Every `_stmt` is a closed `def <x>_stmt : Prop := …`** with an ASCII name and no parameters, at any indentation. Anything else named `_stmt` fails, so no statement can drop out of the audited set.
- **Companions:** at least one `<name>_nonvacuous_stmt`, `<name>_sanity_<k>_stmt` and `<name>_false_variant_stmt`. Each junk-value operation (`/`, `deriv`, `sSup`/`sInf`, ℕ subtraction, `Real.sqrt`/`Real.log`, `tsum`) gets a guard hypothesis that excludes its junk value, listed on the card.
- **Prefer `HasDerivAt` / `ContDiffOn` to `deriv`**, whose value is `0` where a function is not differentiable. Prefer real intervals (`Set.Ici 0`) to ℕ when the paper's variable is real.

### Proof file

```lean
module

public import <Pkg>.Statements.<Name>

set_option linter.style.header false

public section

namespace <Pkg>

theorem nstarAC_part_a : nstarAC_part_a_stmt := by
  unfold nstarAC_part_a_stmt
  ...

end <Pkg>
```

## Every project file (not `.lake/`)

On Windows comparator builds the proofs with no sandbox, so `lean_check` scans every project source first. Code-executing words and kernel bypasses are found anywhere on a line. Syntax extensions are found anywhere in the statement file, and in other files wherever a command can start (so an honest binder named `prefix` is fine). Nothing may import the generated `LeanCheck` library. These are forbidden:
- syntax extensions: `notation`, `infix…`, `prefix`, `postfix`, `macro`, `macro_rules`, `syntax`, `elab`;
- code run during a build: `initialize`, `run_cmd`, `meta`, `#eval` or any other `#` command;
- `import Lean…` or `import Lake…`, and `export`;
- `axiom`, `unsafe`, `implemented_by`, `extern`, `native_decide`, `decide +native`, `skipKernelTC`;
- any `set_option` other than `maxHeartbeats`, `maxRecDepth`, `synthInstance.maxHeartbeats` or `linter.<name> false`.

`sorry` and `admit` are forbidden in the node's own statement and proof files. A `sorry` anywhere the proofs depend on is caught by comparator's axiom check.

## Checks

```
python3 bin/lean_check.py theory/blueprint/<node>.md --hash              # statement-file SHA-256 for the card
python3 bin/lean_check.py theory/blueprint/<node>.md --statements-only --write-report   # formalize stage
python3 bin/lean_check.py theory/blueprint/<node>.md --write-report      # prove stage (full)
```

- **Both modes** check the lakefile, the manifest, the statement file, the card (its SHA-256 and statement list) and every project source. Both clear the project's own `.lake/build` and the `LeanCheck/` folder before building, so nothing compiled or planted earlier can stand in; if either cannot be cleared, the result is UNVERIFIED. Dependencies under `.lake/packages`, and Lake's compiled lakefile cache in `.lake/config`, are kept, and are trusted under the threat model.
- **Statements mode** then builds the statement module. The card may still be unsigned here; signing is checked by the validator.
- **Full mode** adds the proof file. Then it generates a Challenge (the signed statements as `theorem <Pkg>.<x> : <Pkg>.<x>_stmt := sorry`) and a Solution (the proofs), and runs **comparator**. comparator checks that every proof proves exactly its signed statement, with the same definitions underneath, using only propext, Quot.sound and Classical.choice, and replays the solution through the Lean kernel.
- **Verdicts.** PASS needs every check to pass. These are UNVERIFIED: a missing tool, a missing project, a time-out (which kills the whole process tree), or a tool failure inside comparator (shim, lean4export, git). A proof that does not compile is a FAIL.
- **Reports** go in `theory/blueprint/checks/<node>/lean_check_<date>[_n].md`, and none is ever overwritten.
- **Timing:** a full check of the small core-Lean fixture takes about 15 s. With Mathlib, allow a few minutes.
- **Run `lean_check --write-report` yourself, or have the session dispatcher run it, at each approval.** The formalizer never writes reports. The validator rejects a report that names no toolchain that ran, or that carries a FAIL or UNVERIFIED line under a PASS verdict.
- **Threat model.** This catches mistakes, shortcuts and tricks inside the Lean sources and the lakefile. It does not protect against someone with shell access who edits `.lake/packages`, the tools or the reports.
