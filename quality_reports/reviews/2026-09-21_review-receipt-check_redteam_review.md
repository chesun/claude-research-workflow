## Verdict

The gate's happy path and its most important negative cases are sound: an unstaged on-disk receipt, a future-dated receipt, and a receipt older than the code's last commit are all correctly rejected, the fail-open design behaves as intended on malformed input, and the common commit phrasings (`cd … &&`, `-c`/`-C` global flags, env prefixes, `GIT_DIR=…`) are detected and blocked. The design is deliberately permissive (fail-open, heuristic `git commit` detection, a trivial visible waiver), so most trigger-evasions are acknowledged non-issues. The one genuinely serious, *unacknowledged* defect is a **waiver false-trigger**: any `git commit` whose command string contains `REVIEW_WAIVE=1` (or `=true`/`=yes`) after a space — including inside the `-m "…"` message body — silently waives the code gate. This fires precisely on the most likely real-world case: a commit that touches or documents the hook/rule itself. Secondary issues are a day-granular freshness window that lets a same-day pre-edit receipt be reused, an over-broad `**Target:**` matcher, a `PASS`-score false-block, and an all-commits-in-chain waiver scope. The gate is live in this repo (`review.required=true`, registered in settings.json).

## Attacks that did not work (evidence)

- **Unstaged on-disk receipt rejected.** Case H: a perfectly-formed receipt written to `quality_reports/reviews/` but not `git add`-ed → `HOOK_EXIT=2`. `indexed_reviews`/`cat-file -p :path` read the index, not the worktree — forgery-on-disk fails.
- **Future-dated receipt rejected.** Case I: `**Date:** 2099-01-01` → `HOOK_EXIT=2` (`rdate > today` skip).
- **Stale receipt (older than code's last commit) blocked.** Bundled test `stale` and the freshness `since` check: `2020-01-01` receipt against code committed today → exit 2.
- **Duplicate basename does not match on bare basename.** `target_matches('bin/a/tool.sh','tool.sh', {tool.sh:2})` → no match; forces a full-path target when a basename is ambiguous.
- **Suffix-path false match blocked.** `backup/.claude/hooks/new.py` does not match `.claude/hooks/new.py` (leading boundary excludes `/`).
- **Standard commit phrasings detected and blocked:** `git -c …=… commit`, `git -C . commit`, `GIT_DIR=.git git commit`, `cd foo && git commit`, `/abs/path/git commit` (ends-with `/git`), literal-tab-separated `git\tcommit`, extra/leading whitespace — all `(True, …)`; plain unreviewed commit (case E) → exit 2.
- **Fail-open on non-actionable input:** malformed JSON stdin and non-Bash tool events → exit 0 (by design; case K and bundled test).

## Not tested and why

- **Real Windows `git.exe` end-to-end.** The MinGW environment exposes only `git`; non-detection was confirmed at the parse layer (`git.exe commit` → `(False,False)`). Claude Code normally invokes `git`, so operational impact is low.
- **`git ci` alias end-to-end.** Requires a user-configured alias; confirmed miss at parse layer only.
- **Timeout / huge-index DoS.** The hook has a 15s timeout in settings.json and runs several `git`/`cat-file` subprocesses per review; on a very large reviews dir or index it could exceed the budget and be killed. I could not realistically generate a repo large enough; the PreToolUse timeout-then-allow behavior is harness-dependent (likely fail-open, consistent with design).
- **`python3` launcher fragility.** settings.json invokes the hook as `python3`; on this box that resolves to the WindowsApps stub (`…/WindowsApps/python3`). It ran here, but on a machine where that alias is an unconfigured Store redirector the hook would silently not execute and the gate would be absent. This is a registration/environment concern, not a defect in the `.py` itself, so it is noted rather than scored.
