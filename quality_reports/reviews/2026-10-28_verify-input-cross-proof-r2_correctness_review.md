## Verdict

The redesign resolves every round-1 correctness finding exactly as section 6 of the session log claims, and the declined and accepted-limit items check out against the live corpus: CO1 (Case/Subcase) is fixed by `_UNIT` and pinned by `xp_case_numbered`/`xp_subcase`/`xp_base_case`; CO2 (definition false positive) is fixed twice over — "steps used in def:x" no longer even matches (`_ITEM` cannot be an English word) and `verify_input` skips `bc.BASE_KINDS` labels; CO3 (`AND`), CO4 (`_TAIL` list reporting), CO5 (text-order first phrase via min `m.start()`) and CO6 (regression tests) are all verified by sentinel; the RT2 decline reason is real (`cor-gap-rank.md:51` in the BDD repo uses "(def:voluntary-cogcons, Step 1(b))" for the node's own step, pinned allowed by `xp_ok_comma_own_step`); and the RT3 pronoun limit is honestly documented and live (`lem-band.md:33` "its Step 1(ii)" is not flagged). Case scoping is correct: every keyword group is `(?i:...)` while `bc.CITED_RE` is interpolated outside all of them, so an uppercase or mixed-case label (`LEM:B`, `Lem:b`) never matches — consistent with the validator-wide lowercase-label convention. No span component other than `_LBL` can contain a colon, so `CITED_RE.findall(m.group(0))` cannot pick up a spurious label from items, `_KIND` words or separators; the one spurious-label channel is `_TAIL` across a comma boundary (finding 1). `_scan_view` only removes or space-replaces characters the verifier either sees through (markdown/LaTeX wrappers) or cannot see at all (zero-widths), so it keeps every step the verifier can read and the only text it "introduces" is invisible-character normalization. The empty-text contract holds on every return path (the proof-reference problems are appended before the `if problems: return problems, ""` gate), and the CLI exits 0 with input, 1 on refusal with reasons and no input, 2 on usage (`xp_cli_exit_1_no_input`, `vi_cli_usage_exit_2`). All three suites pass — test_blueprint_tools 126/0, test_blueprint_check 187/0, test_lean_check 208/0 — with exactly 52 distinct `xp_` checks executed, none vacuous (refused checks demand empty text plus an item-11 problem naming `lem:b`; allowed checks demand a fully-ready pass with non-empty input); the timing check is meaningful and not flaky (worst 8 ms at 4× the test's input sizes against a 1.0 s bound, measured on strings that previously backtracked exponentially). The docs are accurate, including the live claims: the BDD blueprint has 58 nodes and the scan flags exactly two, both `refuted` variants (`var:band-gamma-zero`, `var:cogcons-wedge-update-cost`), and the three proofs verifiers judged unevenly on 2026-10-15 are each caught — two at `6603e0c^` and `var:vol-commit-equiv-int-tie-continue` in its first version (`dfc5f52`, where it reads "proof of prop:vol-commit-equiv-int"). What remains are three Low edges: a `_TAIL` false positive after the node's own label, a misleading message for non-node label-shaped tokens (`eq:`, `sec:` — none in the live corpus), and a set of documented-floor evasions. Nothing blocks commit.
