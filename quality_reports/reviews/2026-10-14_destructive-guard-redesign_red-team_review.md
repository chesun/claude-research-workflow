# Destructive-guard redesign Review — red-team
**Date:** 2026-10-14
**Reviewer:** red-team critic (independent, general-purpose agent)
**Target:** .claude/hooks/destructive-action-guard.py, .claude/hooks/test_destructive_action_guard.py
**Score:** 62/100
**Status:** Active

## Verdict

The redesign is a real improvement over HEAD — per-segment Tier-1 checking, wrapper/git-option normalization, heredoc-as-data, per-command bypass, and the predicate-based fallback all block classes the baseline let through (verified: `echo hi && git filter-repo ...`, `yes | git push --force`, CRLF chains, `git -C a -C b reset --hard`, `env -i git push -f`, `time -p git reset --hard`, bypass-then-force-push), and it removes the baseline fallback's prose false positive. The regression suite (104 cases) passes. No case was found where the baseline blocked a *genuinely executable* dangerous command that the new guard allows. But under an adversarial lens the new guard fails open against its **own documented guarantees** in three places: (1) a `<<` inside a quoted string is treated as a heredoc, so the new stripper *swallows* subsequent real commands that the new per-segment checker would otherwise have caught — one quoted token defeats the headline fix; (2) `cat <<EOF | bash` executes its body, and the rule doc says a body is checked when "the heredoc line names a shell", yet the implementation only scans words *before* `<<`, so the body is dropped as data; (3) the bypass branch checks later chain segments only against the always-blocked class, so `BYPASS_SHARED_GUARD=1 echo ok && echo '{}' > .claude/settings.json` and `... && rm -rf <Dropbox path>` sail through, contradicting the new "covers only the command it prefixes" paragraph. Wrapper and git-global-option normalization is also evadable at the token level (`env -u X`, glued `-ckey=val`, any unrecognized global option). All findings below carry a repro (string passed to `hook.check_command(cmd, cwd)` with `_shared_prefixes` monkey-patched, exactly as the test suite does); none of the commands was executed. Every fail-open listed was also allowed by the baseline — these are broken new *claims*, not regressions — but two of them (C1, C3) sit squarely inside what the diff says it fixed.

## Findings

### Critical

| Finding | Evidence | Verdict | Recommendation |
|---|---|---|---|
| C1. Quoted `<<` swallows later real commands (Tier 1 and Tier 2). `_HEREDOC_RE` (guard line 451) matches `<<EOF` anywhere in a line, including inside quotes where the shell treats it as literal text. `_split_heredocs` then deletes everything up to a matching terminator line from `outer`, so the per-segment Tier-1 check never sees it. | Repro: `check_command('echo "see <<EOF"\ngit push --force\nEOF', cwd)` → **ALLOW**; the shell executes the force push on line 2. Same with single quotes and `git reset --hard`. Baseline: also ALLOW (it never checked chains). The control shows the swallow is load-bearing: the *unterminated* variant (`'echo "a <<EOF"\ngit push --force'`, no terminator) **BLOCKS**, i.e. without the swallow the new segment checker catches line 2. Tier 3 survives (`_check_settings_write` runs on the original string: swallowed settings write still BLOCKS — probe G1), Tier 1/Tier 2 do not (probe G2: swallowed `rm -rf <shared>` ALLOWS). | WRONG — the new "every command of a chain is checked" guarantee is defeated by one quoted token, and the stripper *removes* a command the new checker would otherwise block | Only honor a `<<` that shlex sees as an unquoted token (e.g. find heredoc operators on the shlex token stream, or at minimum reject a `<<` whose match position lies inside a quoted span). Alternatively: when a heredoc body is dropped as data, still run the Tier-1 segment check over the dropped lines and *advise* (not block) on hits, so a swallow is at least audible. Add regression cases for both quote styles. |
| C2. `cat <<EOF \| bash` body not checked. `_split_heredocs` decides shell-vs-data from `line[:m.start()]` only (guard lines 482–484), so a shell named *after* the `<<` operator never triggers the recursive check — but bash reads the body from the pipe and executes it. The rule doc ("Heredoc bodies are data **unless the heredoc line names a shell** (`bash <<EOF`, `sh -s <<EOF`)") promises more than the code does: here the heredoc line does name a shell. | Repro: `check_command('cat <<EOF | bash\ngit push --force\nEOF', cwd)` → **ALLOW**. Also `'cat <<EOF | sh -\ngit filter-repo --invert-paths\nEOF'` → ALLOW. Baseline: also ALLOW. Control: `'true | bash <<EOF\ngit push --force\nEOF'` (shell named *before* `<<`) → BLOCK, confirming the prefix-only scan is the defect. Not in the documented-limits list (the doc's known limits cover `$(...)`, backticks, `eval`, `sh -c` — not the heredoc-pipe). | WRONG — implementation narrower than its own rule text, on the exact shape (pipe a script into bash) an agent naturally produces | Scan the whole heredoc line (minus the body) for shell names, not just `line[:m.start()]` — the false-positive cost is nil (a body checked unnecessarily is fail-closed). Add `cat <<EOF \| bash` and `cat <<EOF \| sh -` regression cases. |

### High

| Finding | Evidence | Verdict | Recommendation |
|---|---|---|---|
| H1. Bypass branch skips Tier 2 and Tier 3 for later segments. In `check_command` (guard lines 584–592), once the leading `BYPASS_SHARED_GUARD=1` is seen, only `_always_blocked` runs over `segments[1:]`; `_check_settings_write` and the rm/find shared-storage extractors are never reached. The new bypass paragraph in `destructive-actions.md` says the prefix "covers the command it prefixes … the force push is still blocked" — true for Tier 1 only. | Repros: `check_command("BYPASS_SHARED_GUARD=1 echo ok && echo '{}' > .claude/settings.json", cwd)` → **ALLOW** (without the bypass prefix the identical chain BLOCKS — probe E4); `check_command("BYPASS_SHARED_GUARD=1 echo ok && rm -rf <fake-dropbox>/repo", cwd)` → **ALLOW**; newline-separated variants identical (probe G14). Baseline: also ALLOW (whole-command bypass), so not a regression — but the new doc claims per-command scope. Tier-1 chaining after bypass works (`BYPASS_SHARED_GUARD=1 git status && git push --force` → BLOCK; `BYPASS_SHARED_GUARD=1 true && cd x && git rebase main` → BLOCK). | WRONG — documented per-command bypass scope holds for Tier 1 only; an innocuous bypassed first command silently disarms the settings gate and the shared-storage delete gate for the whole chain | In the bypass branch, run `_check_settings_write` per non-bypassed segment (reconstruct via `shlex.join` or pass the segment substring) and run the Tier-2 extractors over non-bypassed segments. Or simplest: after handling the bypassed first segment, re-enter the normal path on the remainder. |
| H2. `env -u X git push --force` evades wrapper normalization. `_normalize`'s wrapper loop (guard lines 433–436) strips option tokens but not an option's *argument*: after `env`, `-u` is dropped, `X` is not, so tokens become `["X","git","push","--force"]` and no predicate matches. Same mechanism: `env -- git push -f` leaves `"--"` in front (the loop explicitly refuses to strip `--`). | Repros: `check_command("env -u X git push --force", cwd)` → **ALLOW**; `check_command("env -- git push -f", cwd)` → **ALLOW**; nested `env A=1 env -u X git push -f` → ALLOW. Controls: `env -i git push -f` → BLOCK, `env A=1 git ... ` → BLOCK, `time -p git reset --hard` → BLOCK. Baseline: all ALLOW (no wrapper handling at all) — not a regression, but the diff's stated purpose ("wrappers … do not hide the subcommand") is incomplete. | WRONG for `-u`/`--` (claimed-fixed surface, one-flag evasion); the rest of the wrapper stripping is sound | Teach the loop `env`'s argument-taking options (`-u`, `-C`, `-S`, `--unset`, `--chdir`, `--split-string`) or, cheaper and safer: after stripping flags, also skip any tokens until one matches a known-command shape — or simply strip `--`, and treat `-u` as consuming the next token. Add regression cases. |

### Medium

| Finding | Evidence | Verdict | Recommendation |
|---|---|---|---|
| M1. Git global-option normalization evadable: glued `-c` form and any unrecognized global option. `-ckey=val` (legal git) is neither in `_GIT_OPT_ARG` nor caught by the `--opt=` branch (guard lines 441–446); an option absent from the hard-coded lists (e.g. `--no-lazy-fetch`, git ≥ 2.45) breaks the scan loop. | Repros: `check_command("git -cuser.name=x push --force", cwd)` → **ALLOW**; `check_command("git --no-lazy-fetch push --force", cwd)` → **ALLOW**. | M2. Tier 2 (rm -rf / find -delete on shared storage) is first-command-only; chains evade it trivially. | M3. `cd <shared>; rm -rf …` with the semicolon glued to the path misses the cd-chain. `_consume_cd_chain` requires `tokens[2] in ("&&", ";")` (guard line 393); plain `shlex.split` leaves `repo;` as one token, so the chain is not consumed, `tokens[0]=="cd"`, and no extractor fires. | Repro: `check_command("cd <fake-dropbox>/repo; rm -rf output", cwd)` → **ALLOW**; spaced variant (`… ;  rm …`) → BLOCK. Baseline: identical. | WEAK — pre-existing, but the new `_parsed_segments` splits this correctly and could feed the cd-chain | Derive the cd-chain from `_parsed_segments` output (where `;` is already a separate token) instead of the plain token list. |
| M4. Subshell / brace-group one-character evasions: `(git push --force)` and `{ git push --force; }`. `(` and `{` are neither stripped nor segment separators, so `tokens[0]` is `"(git"` / `"{"`. The doc's known-limits list (`$(...)`, backticks, `eval`, `sh -c`) does not mention them. | Repros: `check_command("(git push --force)", cwd)` → **ALLOW**; `check_command("{ git push --force; }", cwd)` → **ALLOW**. Baseline: identical. | WEAK — same escape class as the documented limits but cheaper to fix than `$()` (no nesting needed: strip leading `(`/`{` and trailing `)`/`;}` per segment, or add `(){}` to punctuation_chars) and currently undocumented | Strip wrapping subshell/brace punctuation per segment, or add the two forms to the known-limits list so the doc stops under-stating the escape surface. |
| M5. `git push origin +main` (forced refspec without a colon) not matched. `_is_force_push` requires `":" in t` for `+`-refspecs (guard lines 77–79); `git push origin +main` is a legal forced push. | Repro: `check_command("git push origin +main", cwd)` → **ALLOW**; `git push origin +main:main` → BLOCK. Baseline: identical (predicate unchanged). | WEAK — pre-existing predicate gap, in scope for a rule that names `+refspec` as blocked | Treat any non-flag arg beginning `+` (after the remote) as a force refspec; a false positive on a branch literally named `+foo` is acceptable for a bypassable guard. |
| M6. `_SHELLS` omits `pwsh`/`powershell`; `py`-launcher omitted from the Tier-3 interpreter list. On this Windows machine both are the natural spellings. | Repros: `check_command("pwsh <<EOF\ngit push --force\nEOF", cwd)` → **ALLOW** (body dropped as data; pwsh executes stdin); `check_command("py -c 'open(\".claude/settings.json\",\"w\").write(\"{}\")'", cwd)` → **ALLOW** (interp regex `python\d*\|node\|ruby\|perl`, guard line 363).
