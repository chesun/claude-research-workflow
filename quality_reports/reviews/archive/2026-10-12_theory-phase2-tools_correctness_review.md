## Verdict

The three tools do what their docstrings and the docs say in the cases the docs describe, and they agree with the validator where they overlap: `verify-input`'s readiness test is the validator's rule for a node at `checked` (`_ready` at `blueprint_tools.py:56-59` versus `blueprint_check.py:561-567`), its `**Target:**`/`**Proof:**` lines are exactly what `proof-verifier.md` tells the agent to copy and what `_report_problem` later checks, every log line `repoint` writes parses under `LOG_RE` and classifies as a `down` move with two existing in-repo locators, and the demotion target (`survived-search`) is the same rung the skill's own FAIL branch uses. The cited-label regex and the `mentions` comment behave as the template states, and the mention really is outside both hashes (pinned by `cl_mention_keeps_hashes`). `agent_lint` reproduces the 2026-10-11 failure class and passes on all 38 agent and skill files. All three suites pass here (117 / 30 / 45). The one High finding is that `verify-input`, which the skill now presents as the whole readiness gate, does not consult the validator for the node itself: it accepts a `proved` node whose proof no longer matches the logged `-> proved` hash (or whose status contradicts its log) and prints the *current* hash, so two verifiers run and their `-> checked` line is then rejected by the validator. The Medium findings are a non-cascading `repoint` that leaves transitive `checked` dependents as validator errors after `--apply`, and a set of behaviours the tests do not pin, including the blindness of the verifier input to the used nodes' proofs and statuses.

### Checked and sound (no finding)

- `repoint` log line versus the validator: actor matches `[a-z-]+`; `proved|checked|formalized|verified -> survived-search` classifies as `down`; locators are two existing regular files inside the repo so the `down` rule is met; `stmt:` is `statement_hash(d.statement)`; a node at `conjecture`/`survived-search` is rewritten without a log line; terminal dependents are skipped; the successor itself is skipped; a dependency cycle is refused before any write (`rp_refuses_cycle`); dedupe when the successor is already in `uses` (`rp_dedupes_existing_successor`); statements naming the old node are reported, never edited. Reordered sections (`## Evidence log` before `## Proof`) and a UTF-8 BOM both round-trip (P8; BOM probe). A `conditional` predecessor with a successor still at `conjecture` and a `checked` dependent gives a PASS blueprint after `--apply` (P13).
- `verify-input` text: statement, proof and used statements are comment-stripped; no `paper_ref`, log, or `[GAP:` reaches the verifier; the hash is `proof_hash(n.proof, n.uses)`, the same function behind `--hashes`; `_ready` refuses `superseded`/`refuted`/below-`checked` claims and non-`stated` definitions.
- Validator: the cited-label warning fires only on non-terminal nodes, ignores comments, self-citations and unknown tokens, prefers the longest label, and respects punctuation boundaries (`cl_*` tests). `mentions` is parsed only from a comment that starts with `mentions:`, exactly as the template says; the preamble is outside both hashed sections.
- `agent_lint` on the repo: 20 agents + 18 skills, 0 problems; the `: ` plain-scalar case, trailing `:`, ` #`, indicator starts, unclosed flow lists, duplicate keys, tabs, block scalars and flow lists all behave as the docstring claims (P10 and `test_agent_lint.py`).

### Unconfirmed

- YAML 1.1 implicit typing: `name: yes`, `model: "..."` are fine, but a bare `yes`/`no`/`on`/`off`/date value is not flagged (P10: `name: yes` and `description: 2026-10-11` → clean). Whether Claude Code's parser coerces these (and then drops or mis-registers the file) was not tested here; PyYAML is not installed on this machine, so no cross-check against a real parser was possible.
- `description: Does:\ta thing.` (colon followed by a tab) is not flagged; YAML treats a tab as whitespace after the colon, so this may be a parse error in Claude Code. Rare enough that it was not pursued.
