## Verdict

The round-1 Criticals are fixed — a proof file that redefines the statements, a `macro_rules` placed as a line head in the proof file, and a `skipKernelTC` forgery in a helper are now all caught (scan reaches every project source, the check file imports `Statements` before `Proofs`, and `leanchecker <Pkg>` re-checks the package). But the gate still does not deliver its one promise, because three new attacks each produce a full-mode PASS for a proof that is not a kernel-checked proof of the signed statement, all run for real against the pinned toolchain (Lean v4.35.0-rc4, fixture copied to `%TEMP%\lcr3`/`lcr4`): (1) **`srcDir = "alt"` in `lakefile.toml`** makes Lake compile a parallel `alt/Fix/Statements/Thing.lean` in which every `_stmt` is `True`, while `lean_check` hashes, parses and card-matches the *real* `Fix/Statements/Thing.lean` it never compiles; (2) a **`lakefile.lean`**, which Lake prefers over `lakefile.toml`, does the same redirection and is worse — the `settings` check reads only `lakefile.toml`, and `project_sources` excludes `lakefile.lean` from the scan; (3) a **helper in sub-namespace `Fix.Fix`** shadows the signed names: because the generated check theorem is declared as `theorem Fix.<x>_check : Fix.<x>_stmt := Fix.<x>`, its own `Fix.` prefix reopens namespace `Fix` during elaboration, so `Fix.<x>_stmt` and `Fix.<x>` re-resolve to `Fix.Fix.<x>_stmt` (= `True`) and `Fix.Fix.<x>` — I confirmed the check theorem's type is `Fix.Fix.thing_part_a_stmt`, not the signed statement, with the proof file empty of any real proof. All three share one root: `lean_check` assumes the files it hashes and scans are the files Lean compiles, and that `{pkg}.{name}` is an absolute reference — neither holds. What is sound: the round-1 fixes above; a trace/olean cache-poisoning attack (forged `True` oleans + replayed traces under genuine sources) was defeated — Lake recompiled and the check FAILed; and all three suites pass (112, 145, 74). The statement/scan command classifier still reads only the first token of a line, so a second command sharing a line escapes it (High, static only). Each Critical has a confirmed, contained remedy; none needs new design.

Repro harness: `%TEMP%\...\scratchpad\r2red\harness.py` builds, per case, a repo (node + card + `lean.toml`) and a fresh fixture copy, plants one defect and calls `lean_check.check_node(node, timeout=900)`. Generated check files and the `alt/` divergence were read directly from the temp projects. Line numbers refer to the staged files.

## Sound (checked, no finding)

- **Round-1 Criticals are fixed.** Proof file redefining the statements → FAIL (`int_rt_proof_redefines_statements_fails`); `macro_rules` as a line head in the proof file → `proof file` FAIL; `skipKernelTC` in a helper → `project files` FAIL; `leanchecker <Pkg>` runs over the package (`rf_leanchecker_whole_package`). Verified by reading the suites and by the macro-hijack live cases failing at `project files`/`build`.
- **Trace/olean cache poisoning is defeated.** Built forged `True` oleans, re-planted them with their genuine traces under restored genuine statements and an *empty* proof file; `lake build --wfail` recompiled and the check FAILed with `unknownIdentifier Fix.thing_sanity_1` (`stale2`). Lake's trace keyed on source content, so stale oleans are not trusted.
- **Proof-file macro/`open..in`/`set_option..in`/`scoped` hijacks fail** — the macro rewrites the proof file's own theorems to `def : True`, tripping `linter.defProp` under `--wfail` (live `oneline_open_in`, `oneline_two_cmds`, `path_dep`, `helper_prefix`). A helper carrying the macro as a line head is caught by `project files`.
- **`srcDir`-independent statement checks** (hash stability under CRLF/BOM, card↔hash↔audited-list binding, statement-of-other-type match, axiom parsing incl. `decide +native`, UNVERIFIED on missing tool/project/timeout, `relaxedAutoImplicit`) behave as in round 1.
- **Suites:** `test_lean_check.py` 112/112, `test_blueprint_check.py` 145/145, `test_blueprint_tools.py` 74/74 on this machine.

## Unconfirmed

- A same-line hidden `macro_rules`/`notation` (escaping #4's scan) placed in a module that the check file imports but whose own theorems it does not touch could in principle hijack the check file without tripping `defProp`. I could not construct one that both escapes the scan and avoids rewriting a scanned module's theorems; the `defProp` linter is a real backstop. If #4 is fixed, the question is moot.
- `project_sources` follows Windows directory junctions (`is_junction` True, `is_symlink` False); a junction into shared storage would be scanned (stricter, not a bypass). Not pursued.
- Substituting the `mathlib` dependency with a fork (lakefile/manifest are outside the card hash): only the revision is recorded, never compared. Same as round 1; low practicality.
