# verify-input cross-proof refusal Review — red-team
**Date:** 2026-10-28
**Reviewer:** red-team critic (independent, general-purpose agent)
**Target:** bin/blueprint_tools.py, bin/test_blueprint_tools.py
**Score:** 68/100
**Status:** Superseded by quality_reports/reviews/2026-10-28_verify-input-cross-proof-r2_red-team_review.md

The change is well built where it aims: all 97 tests pass, the three regexes catch every advertised phrasing (including NBSP, `~`, line breaks, spelled-out "Step two", backticked labels and `\ref{}`), comment stripping is symmetric (the checker and the verifier see the same `_clean` output, so a comment can neither hide a pointer from the checker nor leak one to the verifier), and a scan of all 58 live blueprint nodes produces zero operational false positives (the single hit is `var:band-gamma-zero`, a `refuted` node that can never reach `verify-input`). But as a guarantee it is thin: of 29 realistic evasion phrasings probed, 28 pass through `verify_input` untouched and land in the sealed verifier input — including the two forms the live corpus actually writes, the parenthetical "(label, Step 1(b))" (cor-gap-rank.md:51) and the pronoun "its Step 1(ii)" (lem-band.md:33, a genuine cross-proof pointer in a `checked` node: lem:martingale-horizon's statement contains no "Step"; only its proof does). Separately, rx1's `_ITEMS` subpattern backtracks exponentially: `"step " + "to"*40` takes 1.0 s, doubling every two characters, so a ~150-character token run hangs `verify-input` indefinitely (Python `re` has no timeout). The guard is a useful deterministic floor for the most common literal phrasings, and proof-verifier item 11 remains the backstop; it should be documented and relied on as a floor, not as the refusal the docstring implies, and the ReDoS should be fixed before merge.
