## Verdict

The replacement of the crude substring fallback with `_fallback_check` is a net improvement and the advertised false positives are confirmed gone: prose containing `--force` / `-f ` in heredoc commit messages no longer blocks, the bypass prefix is honoured on the fallback path, and the dangerous classes the old fallback missed entirely (`git clean -fd`, `git rebase -i`, `update-ref -d`, pipe-fed `git clean -fd`) now block with the correct label. The parsed (shlex-succeeds) path is byte-identical in behaviour to HEAD — 21 parseable probe commands produced 0 old-vs-new mismatches — and the shipped suite passes 80/80 (`py -I .claude/hooks/test_destructive_action_guard.py`). The bypass regex resists every abuse form tried (`X=$(BYPASS_SHARED_GUARD=1) …`, `=1x`, `=10`, glued `;`, mid-command placement). However, the fallback has one real fail-open regression: a backslash line continuation splits the flag away from its command, so `git push \<newline> --force …` (and `-f`, `reset \<newline> --hard`, `clean \<newline> -fdx`, `update-ref \<newline> -d`, `+refspec` continuations) pass the fallback while the identical command *without* the stray apostrophe is blocked on the parsed path — and the old fallback blocked the force-push and reset forms too. This is the incident class the hook exists for, caught by both baselines and missed by the new code, hence High. The remaining old-blocked/new-allowed cases ($(…), backticks, `eval`, `sh -c`, `xargs`, `env`, `command`, `git -C`/`-c`, subshell, brace group, single-`&` chain, `python -c`) are exactly as loose as the parsed path for the same command written without the apostrophe, so the effective security boundary is unchanged; they are recorded as pre-existing gaps, not regressions of this diff. All probes were run via `hook.check_command(cmd, "/tmp/foo")` on synthetic strings (never executed); harnesses in the session scratchpad (`rt20261014_probe.py`, `rt20261014_probe2.py`), old baseline from `git show HEAD:.claude/hooks/destructive-action-guard.py`.
