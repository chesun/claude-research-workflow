# sync_status Review — red-team + correctness
**Date:** 2026-10-14
**Reviewer:** red-team + correctness critic (independent, general-purpose agent)
**Target:** bin/sync_status.py, bin/test_sync_status.py
**Score:** 58/100
**Status:** Active

## Verdict

The tool is correct on its happy path — the 13 shipped tests pass, behind/ahead counting, `-z` attribute parsing (including paths with spaces and unicode), the DVC-absent UNVERIFIED path, worktrees, and shallow clones all behave — but it fails its own stated purpose on four realistic inputs, three of them false all-clears. (1) LFS rules in a nested `.gitattributes` (or `info/attributes`, or a macro defined outside the top-level file) disable the *entire* LFS section: a plain blob under an LFS rule yields PASS, and an unpushed LFS file loses the `git lfs push` action, so following the tool's advice pushes broken pointers. (2) When the `git-lfs` CLI is absent, the LFS tier silently prints `0` and PASS instead of the UNVERIFIED the contract promises for exactly this case. (3) A guard pre-push that merely *mentions* "git lfs" in a comment counts as "hook runs", suppressing the `git lfs push` action — the one distinction this tool exists to make on this machine. (4) No-upstream, detached-HEAD, and configured-but-never-fetched upstreams all exit 0 and print "All storage tiers in sync." while commits exist nowhere but locally. Separately, the plain-blob check spawns one `git cat-file` per LFS-attributed file (48.8 s for 300 files measured here; the plan budgets ~200 PDFs), and the exit-code contract's FAIL→1 mapping is never exercised by the test suite. Below the commit gate; the fixes are small and localized.

All repros were built with `git init` under the session temp directory, with hooks passed via `hooks_dir=`/`--hooks-dir`; nothing was pushed and no `core.hooksPath` was touched. Synthetic sentinels only. `py -I bin/test_sync_status.py`: 13 passed, 0 failed (git 2.56.0.windows.2, git-lfs 3.8.0, Python 3.14.8).

## Correctness check — do the tests prove the documented behaviour?

Each shipped test and the mutation that would fail it:

- `ss_clean_repo_in_sync` / `ss_clean_repo_main_exit_0` — verdict computation and PASS→0; breaking `build_report`'s verdict line (sync_status.py:188) or the exit map's PASS entry fails them.
- `ss_ahead_flags_push` — ahead counting and action text; swapping `behind, ahead` at sync_status.py:74 fails it (ahead would read 0).
- `ss_no_upstream_noted` — pins the no-upstream wording **and** `actions == []` (this is finding 4 cemented as spec).
- `ss_plain_under_lfs_flagged` — the `-z` check-attr field stride, the `POINTER_HEAD` sniff, and the renormalize action; corrupting the stride (3→2) or the pointer prefix fails it.
- `ss_lfs_patterns_listed` — the top-level parser; note a fix for finding 1 (nested files) would *not* fail it, so it doesn't block the repair.
- `ss_unpushed_lfs_hook_skipped_flagged` — `unpushed_lfs` ref range, the hook-negative path, and the `origin main` remote/branch split; breaking `partition` or the action text fails it.
- `ss_unpushed_lfs_hook_runs_no_lfs_action` — suppression when the hook runs, while `git push` is still suggested.
- `ss_dvc_without_cli_unverified` / `ss_dvc_without_cli_exit_3` — the UNVERIFIED verdict and the 3 mapping.
- `ss_usage_exit_2`, `ss_missing_dir_exit_2`, `ss_not_a_repo_exit_2` — the three usage-error paths.

Not proven by any test: FAIL→1 via `main()`, behind-only, the backup section, DVC with a working CLI, `--hooks-dir` missing its value, and every input in findings 1–3 (see finding 10).

**SKILL text vs code.** The five bullets in `.claude/skills/tools/SKILL.md:154–161` and the verdict/exit line match the code's intent, and the LFS-quota omission is documented. Two bullets overstate what the code does: "files committed as plain blobs although `.gitattributes` routes them to LFS" is only true for the *top-level* `.gitattributes` (finding 1), and "when Git LFS's own pre-push hook does not run" is decided by a comment-blind substring heuristic (finding 3). Relative to plan §7.5 (a DRAFT), endpoint/bandwidth/pending-downloads/pointer-count/stale-paths were dropped; the SKILL documents only the quota omission — acceptable, since the SKILL is the operative doc, but pointer count and stale paths vanished without a stated reason. The usage line, exit codes, and backup path (`~/Dropbox/research-data/<repo>/backup/`, sync_status.py:113) match exactly. Stdlib-only requirement: satisfied.

**Read-only claim.** `main`/`build_report` write nothing themselves (all git subcommands invoked are read-only; verified by inspection of every call site). The one caveat is `dvc status -c`, which as a side effect of the DVC CLI takes DVC's lock in `.dvc/tmp` — outside the script's control and harmless, but "never writes anything" should be read as "issues no write commands".
