## Verdict

The fail-closed core is sound where it matters most: I could **not** brick non-gated Bash and I could **not** lock out despite the waiver. Exit 2 is reachable only after the command is confirmed to be a `git commit`, `review.required` is `true`, and the commit is not waived — so `ls`, `git status`, non-git commands, and commits in non-opted-in repos all fail open (exit 0), and every fallible git call sits behind the waiver short-circuit, which is parsed before any subprocess runs. Benign non-zero git states I feared (no-HEAD first commit, detached HEAD, in-progress merge) all evaluate cleanly and block/allow correctly rather than throwing a spurious GATE ERROR. The deductions are for one real shipped bug (`Path` is used but never imported, so the failures log the fail-closed banner points users to is **never written**), a coverage gap versus the spec (extensionless `bin/` scripts are silently not gated), and two silent-scope foot-guns (subshell/pipeline-wrapped commits and a non-`true` config value both bypass the gate quietly). None of these can brick a session or cause a wrong block; they degrade auditability and gate coverage.

## Attacks that did not work (with evidence)

- **Session-brick via fail-closed leaking to non-gated Bash (Attack 1) — SOUND.** In a gated repo, `ls -la`, `git status`, and `rm -rf /tmp/whatever` all returned `EXIT=0`. Exit 2 is structurally unreachable before the command is confirmed a `git commit` (parse is string-only; any exception before confirmation is caught by the `__main__` backstop → exit 0) and before `review.required=true`. Non-Bash tool events and malformed stdin also exit 0.
- **Lockout despite the waiver (Attack 2) — SOUND.** The waiver is parsed and honored (lines 311/316) before the config read and before the try-block that can fail closed. In-process test: `REVIEW_WAIVE=1 git commit` with `staged_changes` forced to raise returned `0` (short-circuit before the failing call). Even on a shlex parse error the fallback `seg.split()` still detects the leading `REVIEW_WAIVE=1` token. The documented form always escapes; no state locks out.
- **False fail-closed on benign git states (Attack 3) — SOUND.** No-HEAD first commit (block correct with unreviewed code; receipt honored when present), detached HEAD (clean block), and an in-progress merge with a conflicted file + code staged by the merge (clean block) all produced the ordinary BLOCKED path, never a GATE ERROR banner. `staged_changes` (`git diff --cached`) and `last_commit_date` (tolerant `git_soft log`) both survive a no-HEAD repo.
- **Silent-disable of a genuine block (Attack 4) — mostly SOUND.** No path found where staged unreviewed code in an opted-in repo exits 0 with a receipt genuinely absent, aside from the classification gaps recorded above (extensionless `bin/`, wrapped commands, non-`true` config). The `git_soft` tolerance in `last_commit_date` only weakens freshness on a no-HEAD repo, where vacuous-true is the correct answer.
- **Waiver false-trigger / message-body evasion (Attack 5) — SOUND.** `git commit -m "…REVIEW_WAIVE=1…"` is detected as a commit and blocked (not waived); the token is honored only as a leading env assignment of the commit segment. `git -c a.b=c commit` is detected; `git commit-tree` and `git -c foo.bar=commit status` are correctly not treated as commits.
- **Failures log escaping the repo / crashing the hook (Attack 6) — SOUND on crash-safety.** `_log_failure` is fully wrapped in `try/except: pass`, so its (currently guaranteed) `NameError` cannot take down the hook — the trade-off is that it also never writes (the Medium finding above). It never writes outside the repo: root is derived from `git rev-parse --show-toplevel`.

## Not tested and why

- **Real Claude Code hook wiring / subagent dispatch** — cannot invoke the live PreToolUse pipeline from here; exercised the deployed script directly with faithful fake events instead (same code path the harness runs).
- **Non-ASCII / quoted paths, review-file-staged-as-deletion, huge/binary staged files** — the `-z`/`core.quotePath=false`/`--diff-filter=ACMRD` plumbing is standard and the block decision depends only on path strings; time-boxed to the higher-yield scoping and fail-closed attacks. A deletion of a review file simply drops it from `ls-files --cached`, which at worst removes a receipt (fail-closed-safe direction).
- **Windows path-separator matching in `target_matches`** — the code normalizes `\\`→`/`; not adversarially fuzzed.
- **Concurrent commits / TOCTOU between staged read and the actual commit** — out of scope for a single-process PreToolUse gate.
