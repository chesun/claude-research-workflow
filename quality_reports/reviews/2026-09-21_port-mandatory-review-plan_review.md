## Verdict

The port is **faithful and would function** — the mechanism (receipt detection, `**Target:**` path/basename/ADR match, day-granular freshness vs last-commit, audited waiver, fail-closed) is copied intact from the sibling guard, and its two headline premises verify **true**: this repo's `core.hooksPath` genuinely comes from the global `~/.gitconfig` (local scope unset), so a local override would in fact drop the machine guards, and the delegation shims are the right way to preserve them. That said, the plan is **not efficient and mildly over-scoped for this user**: it reaches for the sibling's git-hook + `core.hooksPath`-override machinery — the single most invasive option — without considering a materially simpler design that matches this repo's *existing* gate architecture (every current gate is a Claude Code `PreToolUse`/`PostToolUse`/`Stop` hook, not a git hook). It also under-states three real costs: (a) `core.hooksPath` is local-only config, never committed, so the gate is **inert on every fresh clone and on the Mac** until manually re-wired; (b) each gated commit triggers a ~300–600k-token, 10–20-min two-agent cycle (per ADR-0016) on a repo whose *primary activity is editing exactly the gated files*, making this by far the heaviest of the "kept" gates and in tension with the pruning philosophy it invokes; (c) dropping the commit-msg scrub scan rests on an unverified assumption that the machine push guard re-scans message bodies. Not bloated in its code (the ~300-line guard earns its length), but bloated in *mechanism choice* and *gated-set breadth*. Fit for purpose with fixes; fix the mechanism question before building.

## What the plan gets right

- **Both headline premises verify true.** `core.hooksPath` really is global-only here (origin `~/.gitconfig`, local unset), so the conflict is real and git precedence (local > global) really would drop the machine guards. The plan diagnosed this correctly rather than hand-waving.
- **Delegation "if present, else allow" is genuinely inert on a fork and on the Mac** (no `<guard home>` → allow), while preserving machine protection on the work laptop. That design fork is recommended correctly.
- **Decoupling the opt-in from the machine guards' repository-class setting to a repo-local `review.required`** is the right call for a shareable template — clean, generic, portable. Recommended correctly.
- **The receipt logic is ported faithfully and each function earns its place** — path/basename/ADR match, rename-follows-old-path freshness, doc-line threshold, audited waiver, fail-closed. This is not code bloat; a smaller guard would only mean fewer features.
- **The dogfood step is not blocking-circular.** New files have no last-commit date, so `receipt_for` skips the freshness test; a staged, today-dated report is a valid receipt. The bootstrapping commit passes.
- **A test harness for a fail-closed blocking gate is prudent, not over-engineering** — a bug here locks the author out of committing.
- **ADR numbering (0002) is correct** (`decisions/` holds `0001` + README).

## Sharpest single recommendation

Before building anything, decide the mechanism deliberately: prototype the review gate as a **`PreToolUse` Bash hook that intercepts `git commit`** (identical receipt check, identical waiver) and compare it head-to-head with the git-hook + `core.hooksPath`-override design. The Bash-hook version deletes the plan's entire highest-risk surface — no override of the machine `core.hooksPath`, no delegation shims, no dropped commit-msg scrub, no per-clone/per-machine re-wiring, no collision with the machine AI-gate — and it matches the mechanism every other gate in this repo already uses. Adopt the git-hook design only if coverage of *manual, outside-Claude-Code* commits is a stated requirement; for a strictly-personal repo committed through `/commit`, it almost certainly is not, and the simpler hook is both more consistent and cheaper to own.
