# Theory phase-2 plan Review — efficiency
**Date:** 2026-10-12

**Target:** quality_reports/plans/2026-10-12_theory-workflow-phase2-lean-plan.md
**Score:** 64/100

## Verdict

The plan is structurally sound and reuses phase 1 well (one validator, stdlib `bin/`, injected runner with fakes, review-then-commit), but it spends the expensive and uncertain work in the wrong order. It builds nine tasks of general machinery (script, validator rules, review, templates, two agents, skill modes, auditor guide, docs) before the first Lean statement of the pilot exists, even though phase 1 showed the pilot reshapes the tooling (session log §6 "What to change before phase 2": four items; calibration round 1 invalidated by the pilot). Its agent design has the formalizer prove the theorem before the owner has audited the statement, although the plan's own ladder makes `formalized` depend only on the signed card, so a rejected statement wastes the single most expensive step. The pilot is scoped as a five-part conjunction with multivariate partial derivatives and no budget or stop rule other than "if (d) proves too costly", with "too costly" undefined. Several smaller mechanisms are duplicated or built before need: a custom Lean block parser for the statement hash, a per-declaration whitelist for a token scan that `#print axioms` already subsumes, a second 7 GB Mathlib project, a web-sourced auditor guide written before the owner has read a single card, and a second agent file for a one-paragraph blind prompt. One clause would silently void acceptance #7 on this machine: the integration tests run "only when `lake` is on PATH", and `lake` is not on the shell PATH Claude Code uses here.

## Leaner plan

- **Task 0 — vertical slice in the spike project (hand-driven, half a day).** Rename `spike` → `bdd`. Write `Statements/NstarOpt.lean` (parts (a)–(c) only, with its defs), a `sorry` proof, a hand-written `Check/` file. Run `lake build --wfail`, `lake env lean Check/…`, `leanchecker` by hand; note wall-clock. Hand-draft one fidelity card; the owner reads it unaided and times it. Decide from this: card length limit, whether the `_stmt`/`_check` pattern holds under the module system, and whether (d)–(e) are a second node.
- **Task 1 — `bin/lean_check.py` + tests (fakes).** Whole-file statement hash with the existing `_normalize`; toolchain resolver with the `~/.elan/bin` fallback; file-level token scan with same-line `allow` markers; axiom regexes copied from `lean-lsp-mcp`'s `verify.py`; verdict assembly; report rendering.
- **Task 2 — real runner + fixture.** Core-only fixture project; the five acceptance-#7 cases; integration tests actually run here because of the resolver.
- **Task 3 — validator rules** for `checked -> formalized` (signed card) and `formalized -> verified` (card + PASS report, same SHA). Tests as planned minus the `lean:`-vs-report redundancy.
- **Task 4 — ADR-0002 review and commit of `bin/`.** One round; a second only on a design change.
- **Task 5 — `formalizer` agent (statement-first) and `fidelity-card.md`;** one `lean-layout.md` instead of four Lean templates. Back-translation is an inline blind dispatch from the skill.
- **Task 6 — `/theory formalize <label>` (statement + companions + card → owner signs → `formalized`) and `/theory prove <label>` (proof → `lean-check` → owner approves `verified`).** Budgets in the skill text: ≤ 2 formalizer dispatches per step, card glossary ≤ ~15 symbols, stop and read out on overrun.
- **Task 7 — pilot (a)–(c)** on BDD with `.claude/state/lean.toml`, the mentions pass scheduled and counted. Then (d)–(e) as a second node only if the first reached `verified` within budget.
- **Task 8 — read-out** (cost per step, what the card and companions caught, owner reading time), then the auditor guide written from the owner's actual questions, then docs (`agents.md`, `CLAUDE.md`, `CHANGELOG.md`). Overlay sync deferred to the Track A full sync.
