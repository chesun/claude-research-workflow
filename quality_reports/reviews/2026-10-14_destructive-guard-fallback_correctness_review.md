## Verdict

The change does what the TODO claims: the shlex-failure fallback now splits the command into shell segments, tokenizes each, and applies the same `ALWAYS_BLOCKED` predicates (with the same `_strip_env_assignments`) instead of the old substring heuristic, so prose that merely mentions `--force` or `update-ref -d` beside an apostrophe passes, a real dangerous command still blocks fail-closed, and the block banner now carries the real command's label (verified by probe: `Matched: git update-ref -d`, `Matched: git push --force / -f / +refspec`). Tier 2 (shared-storage deletes) and Tier 3 (settings writes) remain fail-open on the fallback path, which matches the old fallback exactly (`git show HEAD` lines around `check_command`: the old `except ValueError` branch only checked `ALWAYS_BLOCKED` substrings and returned `None` otherwise; `_check_settings_write` independently bails on `ValueError` at guard.py:287–289). All 80 runtime cases pass (`py -I .claude/hooks/test_destructive_action_guard.py` → `80 passed, 0 failed`); no other test file imports the guard. The defects found are at the edges: the bypass taken on the fallback path is not recorded in the audit log (`"bypass": false` is written, contradicting the rule doc's bypass-audit contract), the new `debug["fallback"]` key never reaches the log, the TODO's second named case (`update-ref -d`) has no regression test, and a single `&` is not a segment separator so one narrow class the old fallback blocked is now allowed. None of these lets a first-command destructive operation through, so the core guard property holds.
