## Verdict

The move to comparator holds where comparator is in charge: every proof-level attack from rounds 1 and 2 is still caught, and nothing I tried slipped a wrong proof past the Challenge/Solution comparison or the kernel replay. The weaknesses are now all in what `lean_check` hands comparator and in what the owner reads versus what Lean compiles. Two of them yield a validator-accepted `verified` for a statement whose compiled meaning is not what the owner audits, both inside the stated threat model and with no edits to `.lake/packages`, the tools, or the reports: (1) `lake-manifest.json` is never validated, and Lake follows its `url`/`rev` offline, so the "Mathlib" dependency is trusted on faith; (2) the Mathlib-only import rule is enforced only at column 0, so an indented import routes a statement's meaning into a file that is not hashed and can change after signing. Two further issues are High: the generated `LeanCheck/` library is excluded from the project scan yet is importable and gitignored, defeating the "defence in depth" scan the Windows (sandbox-less) path relies on; and the statement-file reader lets helper names shadow/rebind the standard names the owner trusts (dotted names, `open … renaming`, Unicode homoglyphs). All four suites pass (unit 158, validator 145, tools 74, integration 13), so none of these is currently covered. Every repro was run on the real toolchain and comparator in a temp copy of the fixture under `%TEMP%`; the repo, `~/lean/bdd` and `~/lean/_tools` were not modified.

## Findings

TM = inside the stated threat model (Lean-level mistakes/tricks in project sources and lakefile; NOT shell-level edits of `.lake/packages`, tools, or reports).

| # | Severity | Finding | Evidence | Verdict | Recommendation |
|---|---|---|---|---|---|
| 1 | Critical (TM: yes) | **The dependency manifest is trusted, not validated.** `lakefile_problems` (lean_check.py:343-378) inspects only `lakefile.toml`. `lake-manifest.json` is read solely to copy a `rev` string into the report (lean_check.py:583-585). Lake resolves dependencies from the manifest's recorded location and revision, so the identity of the "Mathlib" the proofs build against is never checked against the canonical upstream. A manifest that records a non-canonical source for the `mathlib` package, with the canonical `[[require]]` still in `lakefile.toml`, is accepted; both statements mode and full mode return PASS and the validator accepts `verified`. Because comparator's own assumption 1 is a *trusted* lakefile-and-import-closure, this is squarely the configuration the tool is responsible for pinning. | Repro project `%TEMP%\rtB\proj`; `scratchpad\drive.py` → PASS (statements) and PASS (full); `scratchpad\e2e.py` → `VALIDATOR: PASS errors: [] warnings: []`. The resolved dependency also followed a later `rev` change in the manifest on the next build. | WRONG | Validate the manifest alongside the lakefile: require `packagesDir == ".lake/packages"`; require the `mathlib` package to be a git dependency whose URL is the canonical `leanprover-community/mathlib4` upstream; reject any local-path or non-canonical-URL package; FAIL before invoking `lake` otherwise. Pin the expected Mathlib revision (in `.claude/state/lean.toml` or on the card) and compare it against both the manifest and the actually-checked-out `git rev-parse HEAD` / `remote get-url` of `.lake/packages/mathlib`; report those resolved values rather than the manifest string. Add an integration case that a non-canonical manifest source FAILs. |
| 2 | Critical (TM: yes) | **Statement-file import and command rules are enforced only at column 0.** `parse_statement_file` applies the Mathlib-only import check under `if head == "import" and top` (lean_check.py:272) and rejects unexpected commands only when `top` is true (lean_check.py:269). Lean accepts an indented header import. An indented import therefore passes the readability rules and pulls another module into the statement's trusted closure without that module being part of the hashed file. Because only the statement file is hashed onto the card, the meaning of a signed statement can then be altered after signing by editing the imported (unhashed) file, and full mode still PASSes with the card's SHA unchanged. | lean_check.py:269,272; `scratchpad\static.py` case `indented_import` → `problems=[]`; `scratchpad\expV2` signed state FAILs, then PASSes after editing the imported helper, statement-file SHA identical before/after (`92199195e2f7bfdf…`). | WRONG | Enforce the import allowlist and the command-position rules on every line regardless of indentation; in a `module`-system statement file a non-column-0 command has no legitimate use, so treat it as a problem. Better, derive the import closure from Lean after the build (e.g. `lean --deps` on the statement module) and FAIL if anything outside `Init`/`Mathlib*` appears, rather than trusting the text scan. Add the indented-import case to both suites. |
| 3 | High (TM: yes) | **The generated `LeanCheck/` library is scan-exempt but importable and gitignored.** `project_sources` skips `rel[0] in (".lake", CHECK_LIB)` (lean_check.py:462-470) and `lean_check` only rewrites its own three generated files (lean_check.py:611-623); any other file placed in that folder survives, is compiled by the `LeanCheck.+` glob, is gitignored (templates/theory/lean-layout.md:63), and so never appears in the Lean repo's diff. A proof file may import such a module (the proof-file check requires only the Statements import, lean_check.py:564-566). On the sandbox-less Windows path this means code in that folder executes during comparator's build while `lean_check` still reports "no code run during builds" and an overall PASS — defeating precisely the defence-in-depth the design cites for the missing sandbox. | lean_check.py:462-470, 611-623; confirmed a build-time side effect occurred during a full run that still reported PASS, using a planted file in the exempt folder. Module-system note: the trivial `import Lean` form is rejected by the `module` import rule, but build-time elaboration commands are not. | WEAK | Scan the `LeanCheck/` contents too (it is attacker-reachable), or regenerate the folder from empty each run: delete it before writing the three generated files so no extra module can persist. Also forbid proof/statement files from importing `LeanCheck.*`. Add a regression planting an extra file in the folder. |
| 4 | High (TM: yes) | **Helper names can shadow or rebind the standard names the owner reads.** The statement-file reader enforces structure but not that identifiers mean what they appear to. Dotted helper names (e.g. a `def` whose name is a dotted path colliding with a core/Mathlib name) are accepted and resolve ahead of the standard name inside the namespace; `open … renaming x → y` rebinds a standard operation to a different one; and Greek-letter / zero-width homoglyphs produce helper identifiers that render identically to standard ones. ## Unconfirmed (suspicions, not substantiated)

- **`lake env <comparator>` PATH/olean ordering:** comparator loads `lean4export`/`landrun` from env paths that `lean_check` sets (lean_check.py:593-594), but it also inherits the parent PATH; a project that places a `lake`/`git`/`lean` shim earlier on PATH could in principle influence the sandboxed build. Not reproduced; the Windows shim already runs unsandboxed, so this is lower marginal risk than findings 1-3. Worth a look if PATH is ever attacker-influenced.
- **TOML quoted-key / duplicate-table tricks on `lakefile.toml`:** `tomllib` rejected duplicate tables in quick trials, and `flat()` (lean_check.py:356-361) flattens nested `leanOptions`; I did not find a parse divergence between `tomllib` and Lake's TOML reader, but did not exhaustively fuzz it. The canonical-key allowlist (lean_check.py:353) limits the blast radius.
- **`definition_names` unused:** the generated config omits `definition_names` (lean_check.py:620-623) and the statements are plain `Prop` defs proved as theorems, so the comparator "definition hole" gaming path (README lines 88-138) does not apply as currently generated. If the layout ever lets a statement leave a `def` body for the solution to fill, revisit.

## Score and findings by severity

The proof-soundness core delegated to comparator is sound against every attack tried; the failures are all in `lean_check`'s configuration-trust and text-reading layers, none of them caught by the passing test suites.
